Interview Playbook · 第 1 题

数据引擎到底是做什么的？
功能、技术、承接三条线讲清楚

这不是把七个模块背一遍的题。面试官想确认的是：你有没有搞清楚引擎的边界—— 谁调它、传什么进去、它做完什么、返回什么、什么不归它管。

纯 SDK · 0 个 REST 接口 核心模块 3032 个 Java 文件 处理器 23 / 8 / 14 数据源插件 63 个
00

先说结论：30 秒能背的版本

数据引擎是智能分析的取数执行层。上层——仪表板、自由报表、大屏、语义模型预览、ChatBI——负责把 「用户要看什么」翻译成一个查询描述器 QuerySchemaParam，交给引擎；引擎负责把它变成能跑的 SQL、 选对数据源执行、把结果算完，返回一个统一的 DataResult。

它是纯 SDK，对外零个 REST 接口——没有 Controller，谁调它谁就得自己传 QuerySchemaParam。 所以「引擎做了什么」有个很干净的答案：从 QuerySchemaParam 进 EngineContext 开始， 到 DataResult 交回去为止，中间全是引擎的事。往上的业务语义、往下的数据库细节都不归它管。

这三句话把边界说清楚了，面试官往下问就有抓手。下面按他问的五个点逐层展开。

01

功能面：它对外提供什么能力

引擎对外就一个契约：描述器进、结果出。为了完成这一次转换，它提供六类能力。

① 查询编排

一次查询不是一次 SQL。分页要总数、交叉表要小计、累计字段要承前行——同一份描述器复制出多个派生上下文，各跑各的，最后合并回一个 DataResult。

StandardFlowExecutor → prepareEngineContext → preExec → realExec → afterExec
② SQL 生成

不拼字符串，先构造 QrySchemaBlock（select/from/where/group/having/order/limit 七段），再按方言翻译。查询块是可被改写的中间表示——权限要加条件、多语要裁表、RBO 要动 AST。

CommonSqlCreator → SqlFactory.assembleSQL3 → SqlDTO
③ SQL 治理

配置驱动的会话优化：按「租户@用户@对象」匹配，依次注入 SET 参数、hint、强制索引、RBO 开关；8 条规则做 AST 等价改写；任一阶段异常整条回退原 SQL。

MatchSqlOptimizeConfig · BloodRelUtils · 5 方言工厂
④ 结果计算

SQL 算不了的拉回内存算：公式拆成「DB 表达式 + 内存表达式」两半，同比环比扩取分页，累计字段补前缀查询，再做行列转换、枚举翻译、TopN 补行。

FormulaSplitter · UniformFormulaResultComputer · SeqCumulativeCalculation
⑤ 权限与安全

字段权限只交接策略不改 SQL；数据权限必须改 SQL 或生成 no-data；租户隔离在终稿阶段统一加；SQL 注入前置拦截；schema 映射由 visitor 改写。

addExtraSqlPart 六步 · getFinalQuery · AntiSqlInjectionPreProcessor
⑥ 数据源接入

63 个插件靠约定发现，不靠 if-else：每个模块放一份 META-INF/intelliv.datasource.plugin，启动扫描登记，门面按方言取连接与 actuator。引擎本身不认识任何具体数据库。

PluginInfoLoader · DriverClassLoader · PluginProvider

编排的核心是「派生上下文」

这是理解引擎的第一把钥匙：一次查询不是一次 SQL。分页要总数、交叉表要小计合计、累积字段要承前行、同比环比要扩取分页—— 这些都是同一份描述器复制出来、换个 ProcessorType 再跑一遍，最后把结果合并回同一个 DataResult。

SQL 治理：为什么不交给数据库

报表 SQL 是平台自己生成的，结构完全可控。用户删掉一个指标，那个字段就没被 SELECT 引用，但它所在的表还在 FROM 里—— 这种「用不到的表和字段」是可以确定性判断的，不是概率问题。所以做规则改写（RBO）比等数据库 CBO 更确定、更可验证。

分派：一次查询有 6 条可能的执行路径

QueryActionFactory#getAction 按上下文分流。这条很重要：面试官如果问「所有查询都是生成 SQL 跑 JDBC 吗」，答案是不是—— 有 5 条非 SQL 路径，REST 数据源根本不存在 SQL 这个概念。

无状态：一个库，不是一个服务

引擎模块里 @RestController 的数量是 0。它被打成 SDK，谁引它的 jar 谁负责暴露接口、负责鉴权、负责开事务。

技术上：天然无状态，可水平扩展，可以在同进程内被多个业务直接调用，没有 RPC 开销。
面试上：回答「怎么承接上层」时这句话最省事——「我们不是一个服务，上层是直接调我们的 jar」。

03

承接：上层分析怎么跟引擎联通

这是五个问点里最关键的一个，因为它决定了你能不能把「引擎」和「产品」串起来。答案分三层：谁在调、怎么调、调完怎么回去。

三条线的差异，正好是「引擎不管业务」的证据

  • 报表线最复杂：先加载 AnalysisModel，按查询桶决定页签与区域的执行批次，再由区域类型决定描述器怎么构造——分组表构造分组维度+指标+合计，交叉表构造行维+列维+交叉点，透视表还要行维指标。
  • 语义线最直接：SemanticModelDTO + 字段列表 → modelToQueryParam，一步到位。
  • 智能线最特别：SemanticFrom 不复用 modelToQueryParam，它先调 getEngineExecInfoDTO 拿模型执行信息和场景权限，再用 builder 自己拼参数。

一个容易加分的细节：ChatBI 还有第二条执行路

SqlTransferExecSqlServiceImpl 拿到外部已经生成好的 SQL 后，直接调 QueryEngineUtil.executeSql(sqlDto, wbDataSource)， 跳过 SQL 生成，只用引擎的执行和数据源能力。所以引擎对上层是「生成+执行」和「只执行」两种服务形态都支持。

最后这条特别值得讲：引擎算出「这个字段你不能看」，但它不改值。改值是导出、打印、推送这些输出端的事。 这个分工很多人答不上来，但它恰恰说明了引擎的边界感——引擎只负责取数和标记，不负责业务呈现。

04

边界：引擎做了什么、没做什么

这一段建议主动讲，因为它能挡住后面一半的追问。

✓ 引擎做

  • 描述器 → 执行上下文
  • 生成 SQL、按方言翻译
  • AST 改写、RBO、hint、强制索引
  • 选 action、选执行器、执行 SQL
  • 算公式、高级计算、累计、小计
  • 加数据权限、租户隔离
  • 返回 DataResult

✕ 引擎不做

  • 不定义语义模型、字段、场景（模型侧）
  • 不决定什么时候查询（报表 / Agent 编排）
  • 不做 CBO——那是数据库内部的事
  • 不管理数据源连接配置（数据源管理）
  • 不决定物化切表（模型 converter 层）
  • 不做字段脱敏（输出侧的事）
  • 不做导出、打印、推送、预警
一句话收口：引擎是 「执行」的 owner，不是「语义」的 owner，也不是「呈现」的 owner。

10 道追问

每题统一三段：他在问什么 → 怎么答 → 代码依据。前 4 道必问，后 6 道往深里挖时才出现。点开看答案。

Q1 为什么引擎不做成微服务，而是做成 SDK？

他在问什么

你有没有架构判断力，还是只会照着现状描述。这题答「因为历史原因」就废了，要说清利弊。

怎么答

「这是刻意的选择，不是没做成。引擎里 @RestController 的数量是 0，项目里每个模块的 artifact 都是 *-sdk——一看就是给别的东西依赖的。

一，它是数据面的计算，不是控制面。一次报表查询要传 QuerySchemaParam——里面有表描述器、几十个 SelectDescriptor、权限设置、派生参数。这些东西序列化过去再反序列化回来，开销可能比查询本身还大。同进程直接调，对象引用传过去就行。

二，事务和线程上下文要跟着走。引擎里到处是 InvocationInfoProxy、ThreadLocalHolder 这类上下文，租户、语言、权限 serviceCode 都挂在线程上。跨服务调用要把这些全序列化带过去，漏一个就是权限错乱。

三，它要跟着业务进程一起扩容。报表服务和引擎是同一个伸缩比——报表多了引擎自然就忙。拆成两个服务反而要各自做容量规划，还多一跳网络。

代价也很明确：版本必须跟业务同步升级。引擎改了入参对象的字段，所有依赖它的服务都得跟着发版，没有「服务端先上、客户端后上」的缓冲。所以引擎的入参对象变更非常保守，宁可加字段也不改字段。」

代码依据

引擎模块 @RestController 数量为 0；模块 artifact：iuap-dp-calcengine-sdk / iuap-dp-queryengine-sdk / iuap-dp-enginesql-sdk / iuap-dp-enginecommon-sdk / iuap-dp-enginemeta-api / iuap-dp-formulatrans-sdk / iuap-dp-enginetest-sdk；根 pom <packaging>pom</packaging>； AbstractFlowExecutor#execInternal 里有 permissionServiceCode 的恢复逻辑，注释明确写着「避免线程复用污染」。

Q2 一次查询要跑几条 SQL？

他在问什么

你知不知道引擎的「派生查询」模型。答「一条」的候选人，说明只看到表面。

怎么答

「不一定，最少 1 条，多的能到 5、6 条。核心机制是派生上下文。

prepareEngineContext 把主 EngineContext 用 KryoUtil.copy 复制几份，每份改一个 ProcessorType，然后各自找自己的处理器去跑： main（主数据，必跑）、count（分页要总数时跑 COUNT(1)）、total（有小计合计时跑，交叉表还可能拆成多条）、 prerow（承前模型要上一页最后一行）、advPreRow（累计计算非第一页，补一段前缀查询）、empty（只查总数或只查合计，主查询标记成 empty 跳过）。

所以「查一个报表」在数据库侧看到的是：COUNT(1) 一条、主分页一条、可能再加小计一条、承前一条。这也是慢查询排查的关键——用户说「报表很慢」，可能是主查询快、COUNT(1) 慢，因为 count 要去排序、要去重。

还有两个优化点值得说：
一是 count 有缓存。countCache 是 Guava 的 Cache<String, Integer>，容量 1000、24 小时，key 用临时表名。同一个报表翻页不重复查总数。
二是 count 会去排序。getSelectSql4Count 里调 removeOrder，但只去 limit == null 那一层的排序——因为带 limit 的排序会影响截取哪批数据，去掉就错了。这个细节很容易被问。」

代码依据

AbstractFlowExecutor#prepareEngineContext 派生 pageCountContext / totalContext / preRowContext，方式是 KryoUtil.copy(engineContext) 再改 ProcessorType； PageCountQueryProcessor 里 countCache.getIfPresent(cacheKey) 命中直接 setTotalCount，miss 才 getRowsCount()； TotalResultUtils#countCache = CacheUtils.buildCache(1000, 24, TimeUnit.HOURS)； CommonSqlCreator#getSelectSql4Count 构造 COUNT(1) 后调 removeOrder，内部判断 getLimit() == null 才清排序。

Q3 ProcessorType 为什么要分这几种？

他在问什么

你是背下了枚举，还是理解「为什么是这套切法」。

怎么答

「因为这几种查询在业务上就是不同的东西，不是同一个查询的不同参数。

举个最直白的例子：总数查询和主查询长得几乎一样，但它们不是一回事——主查询要排序、要分页、要返回 20 条明细；总数查询只要一个数字，不能带排序（带了浪费），还要能命中缓存。如果一个方法里用 if 判断「这次要不要算 count」，那个方法会长到没人敢改。

注意两个细节，说明这套设计不是纯理论：
第一，prerow 和 advPreRow 没有自己的专用处理器——它们复用 MainQueryProcessor，靠「上下文里装的是什么」来区分。advPreRow 甚至完全没有 @QryProcessor(advPreRow)，realExec 发现列表空就手工 new 一个 MainQueryProcessor 兜底。这是实用主义，不是洁癖。
第二，empty 不是「不执行」。看名字会以为是空处理器，实际上它会加载 PageCountQueryMainProcessor 和 TotalQueryMainProcessor——只查总数时，主查询确实该空，但总数和合计还得查。这个命名其实有点误导，我第一次读也以为是空跑。」

代码依据

ProcessorType 注释本身就是中文：main("主流程处理器")、count("查询总条数处理器")、prerow("查询承前行处理器")、total("查询小计合计处理器")、advPreRow("高级计算承前处理器")、empty("空处理器, 不进行实际的操作")； 注册清单：MainQueryProcessor 是 @QryProcessor({main, prerow})，PageCountQueryMainProcessor 与 TotalQueryMainProcessor 都是 @QryProcessor({main, empty})，全仓没有 @QryProcessor(advPreRow)； StandardFlowExecutor#realExec 处理器为空时 new MainQueryProcessor 兜底，doSyncExec 没有这个兜底。

Q4 为什么 SQL 生成和 SQL 执行要分两层？

他在问什么

你能不能看出「同一个 SQL 字符串被两拨人改」这个设计意图。

怎么答

「因为两层的关注点完全不同，而且改的时机也不同。

第一层是 SQL 生成：CommonSqlCreator#getSelectSql4Page 把 EngineContext 变成 QrySchemaBlock（七段结构），再由 SqlFactory#assembleSQL3 按方言翻译成 SqlDTO。这层产出的是业务语义正确的 SQL——用户要的字段、条件、分组都在里面了。

第二层是 SQL 终稿：getFinalQuery 在真正下发前再处理一遍，顺序是固定的——占位符替换 → dynamic_schema → schema / AP / 逻辑数据源 visitor → 租户隔离条件 → 追踪注释。然后才进 JdbcDsExecutor，JDBC callback 里再走一遍 hint / force index / RBO。

为什么必须分开？三个理由：
一，schema 和租户这些东西，SQL 生成阶段根本不知道。生成时用的是模型里定义的逻辑表名，物理 schema 要等到真正要连哪个数据源才确定。
二，RBO 和 hint 必须看到最终 SQL。如果先生成再改、改完再改 schema，那改写结果可能被 schema 替换破坏。所以顺序是死的：先业务语义，再环境适配，最后才是性能优化。
三，SQL 预览和真实取数要能复用又不能混淆。querySearchSql 复用了第一层和部分前置处理，但它不执行，返回的是 SQL 文本。如果把生成和执行揉在一起，「预览 SQL」这个功能就得重写一遍生成逻辑——那样两边一定会漂移。

反过来也要说清：不能从 SQL 预览的结果推断真实执行 SQL。预览不做终稿处理；真跑的时候还会加 schema、租户、trace 注释和 RBO 改写。」

代码依据

CommonSqlCreator#getSelectSql4Page / getSelectSql4Count / getSelectSql4All / getSelectSql4View 都调 SqlFactory.assembleSQL3； DataQueryServiceImpl#getFinalQuery 顺序：replaceConditionPlaceHolder → dynamic_schema → schema visitor → handleTenantFilter → 追踪注释； QuerySqlProvider 在 calc-engine/.../flow/model/；hint / force index / RBO 在 SqlOptimizeConfigUtil#execSqlForceIndexAndRboRulesSetting。

Q5 插件化数据源怎么加载、怎么隔离？

他在问什么

你是不是只见过「有 63 个数据源」这个数字，还是真的知道它们怎么进来的。

怎么答

「三个环节：发现 → 登记 → 取用。

发现靠约定文件。每个数据源模块的 resources/META-INF/ 下放一份 intelliv.datasource.plugin，内容包含 name、plugin 类名、type、order。loadSysPlugin 用 Spring 的 PathMatchingResourcePatternResolver 扫 classpath*:/META-INF/intelliv.datasource.plugin，扫到几个就是几个，仓库里现在有 63 个。

登记分两类，这是最容易漏讲的：
系统插件：打包时就跟着 classpath 走，启动时用 PluginURLClassLoader 从 jar 里实例化 actuator，存进 SYS_PROVIDERS；
自定义插件：从 DSConstant.PLUGINS_DATASOURCE 目录读，惰性加载——getPluginData 先查系统再查自定义，都没命中才现场实例化，写进 CUSTOM_PROVIDERS。为什么惰性？自定义插件可能有几十个，一次性全加载会拖慢启动。

隔离靠 DriverClassLoader，它继承 URLClassLoader，重写了 loadClass：先去插件自己的 jar 里找，找不到再交给父加载器。这跟双亲委派的顺序是反的——标准是父优先，这里是子优先。为什么？因为不同数据源可能带同一个驱动类的不同版本，比如两个版本的 ojdbc。子优先能保证插件用自己带的驱动，不跟别人串。

取用统一走 PluginProvider 门面。执行器工厂 SimpleDsExecutorFactory#getExecutor 只看一个东西——AcutatorType 是不是 JDBC。是就 JdbcDsExecutor，不是就 OtherDsExecutor。所以加一个新数据源不需要改引擎任何代码，加一个模块 + 一个描述文件就行。」

代码依据

PluginInfoLoader#start：先 loadSysPlugin() 再 loadCustomPlugin(DSConstant.PLUGINS_DATASOURCE)，最后 Collections.sort； DriverClassLoader extends URLClassLoader，loadClass 里先 findClass 再 super.loadClass（注释：「先从指定Jar包中加载，找不到再从父classLoader加载」）； SimpleDsExecutorFactory#getExecutor：AcutatorType.JDBC.equals(...) → JdbcDsExecutor，否则 OtherDsExecutor；插件数 = find iuap-data-plugin -name "intelliv.datasource.plugin" | wc -l = 63。

Q6 字段权限和数据权限的执行顺序？

他在问什么

权限这块最容易讲成一锅粥。他要看你能不能分清「改 SQL 的」和「不改 SQL 的」。

怎么答

「顺序是固定的，而且分成两个阶段：SQL 生成阶段和生成后处理阶段。

生成阶段，新权限流程直接参与查询块构造：业务对象表走 DataPermissionBizObjTableProcessor#handle，把权限条件加进 querySchema，基础翻译生成 SQL 后再 postHandle 一次；语义脚本表走 SqlConditionAssembler，把命中的表替换成带条件的子查询。

生成后处理阶段，addExtraSqlPart 里是六步固定顺序：① 字段权限自动匹配 → ② 特殊逗号替换 → ③ 数据权限严控（命中就生成无数据 SQL）→ ④ 多角色组织权限严控 → ⑤ 旧数据权限改写 → ⑥ 加注释。

关键区分，一定说清楚：字段权限不改 SQL，数据权限改 SQL。
字段权限是「你无权看这个字段」，但 SQL 里这个字段还得 SELECT 出来——因为要不要展示、要不要脱敏，是输出端决定的。所以引擎只是把策略放进 columnSfStrategyInfoMap 交出去，handleColumnLevelPermission 的返回值是 void，它不碰 SQL 字符串。
数据权限是「你无权看这些行」，那必须在 SQL 里加 WHERE，否则数据都出来了再过滤就晚了。所以它一定是改写 SQL 或者生成 no-data SQL。

还有第五步那个 handelDataPermission 是旧流程。判断条件很绕：新权限流程为真、或者 onlyBizObjTable() 命中，就跳过。而 onlyBizObjTable() 不是字面意思的「只有业务对象表」——commonTableDict 非空且每项都是 BizObjTable / SemanticTable / 带特征的 SourceTable 才返回 true，空字典返回 false。这个细节被问到时说出来会很加分。」

代码依据

addExtraSqlPart 的 ExecuteMonitor.nextWatch 顺序：添加额外SQL片段 → 处理SQL特殊符号 → SQL权限严控 → SQL多角色组织权限严控 → SQL权限处理 → 添加SQL注释； handleColumnLevelPermission 返回 void，写 EngineContext.columnSfStrategyInfoMap； DataPermissionUtil#setAuthCtrl、DataPermissionServiceImpl#addPermissionForSQL 是旧流程 SQL 改写；执行前还有 DataQueryServiceImpl#getFinalQuery 做 schema visitor + handleTenantFilter 租户隔离。

Q7 RBO 和 CBO 的区别？为什么你们不用 CBO？

他在问什么

搞没搞清「数据库内部的优化器」和「应用层自己写的优化器」不是一回事。

怎么答

「CBO 是基于代价的优化，靠统计信息（行数、选择率、索引基数）估算每种执行计划的成本，选最便宜的。这是数据库内部的事，我们既没有准确的统计信息，也没有权限去干预。

RBO 是基于规则的，按固定规则做等价的 AST 改写，不估代价。我们的场景恰好适合 RBO，原因只有一个：报表 SQL 是平台自己生成的，结构完全可控。

举个例子：分组表加一个维度，SQL 里就多一个 LEFT JOIN 和一组 GROUP BY。用户删掉一个指标，那个字段就没被 SELECT 引用了，但它所在的表还在 FROM 里——这种「用不到的表和字段」是可以确定性判断的：外层没引用它、它不在 GROUP BY 里、它没有过滤条件，那就能裁。这不是概率问题，是看 AST 就能得出的事实。

所以我们的定位很明确：在 SQL 生成侧做优化，不跟数据库抢活。数据库该用什么索引、该走 nested loop 还是 hash join，那是 CBO 决定的；我们做的是「少给数据库一些无用功」。

反过来说，如果 SQL 是用户手写的、千奇百怪，那规则改写风险就很大——你不知道那条 LEFT JOIN 是不是故意留着的。我们敢做，是因为输入的形态在我们控制范围内。」

代码依据

BloodRelUtils#process(statement, list) 按配置字符串 ; 分割后顺序执行； 8 条规则：SQLUnionSelectItemUnifyProcessor → SQLSelectAllTrimProcessor → SQLGroupByItemTrimProcessor → SQLTrimSelectItemProcessor → SQLCondExprDedupProcessor → SQLSubQueryTrimProcessor → SQLLeftJoinTrimProcessor → SQLFilterPushDownProcessor（这是无参 process 的全量顺序，不是生产默认顺序）； 生产顺序由 rboRules 配置决定，未知名称静默跳过。

Q8 引擎怎么保证改写后结果一致？

他在问什么

做 AST 改写最怕的就是「改完结果不对」，他想知道你有没有这种敬畏，以及有没有验证手段。

怎么答

「四条防线。

第一，规则本身只做等价变换。我们只做四类事：裁掉没被引用的字段和表、把过滤条件下推到更内层、去掉重复条件、统一 UNION 的项。这四类都是为了消除冗余，不改变结果集。不做的也很明确：不重排 join 顺序、不改聚合逻辑、不动子查询的关联关系。

第二，改的是 AST 不是字符串。用 Druid 的 parser 把 SQL 解析成 SQLStatement，改节点，再 toSQL 打印回来。这样不会出现「正则替换把某个字段名误伤」的问题。不同方言有不同 factory——MySQL / PG / Oracle / DM / 默认兜底五个。

第三，失败就整条回退。execSqlForceIndexAndRboRulesSetting 把 hint、force index、RBO、序列化全包在一个 try 里，任何一步抛异常，直接 return 原始 SQL。所以最坏情况是「没优化」，而不是「优化错了」。这一点很关键，因为半改写的 SQL 比不改写的 SQL 危险得多。

第四，测试。引擎有专门的测试 SDK iuap-dp-enginetest-sdk，能声明表拓扑、Mock 数据源、全流程跑一遍验证结果。query-engine 下面还有 test_cases/ 目录，按功能分：hint、DataPermissionServiceImpl、SqlUtil、QryBlockFieldAliasTrans、DataDesensitizationUtilTest。

有一点我要说清楚：「用 EXPLAIN 对比执行计划」是辅助手段，不是主判断依据。我们的正确性判断主要是「改写前后语义等价」这件事本身能论证，加上单测验证数据一致；EXPLAIN 变化只是说明改写生效了。」

代码依据

execSqlForceIndexAndRboRulesSetting 整段 try-catch，catch (Exception e) { log.error(...) } 后 return querySql； SqlOptimizeFactoryEnums：MYSQL / PG / ORACLE / DM / DEFAULT，DEFAULT 用 MySQLOptimizeFactory； engine-test/README.md：4 套标准基线 baseline_flat_detail.json / baseline_join_semantic.json / baseline_aggregate.json / baseline_pivot.json。

Q9 慢 SQL 怎么定位到具体步骤？

他在问什么

生产上用过的排查手段，不是纸面知识。

怎么答

「引擎有一套分层的埋点，从粗到细。

最粗一层是入口拦截。IntellivSlowInterceptor 实现 AsyncHandlerInterceptor，preHandle 开始计时、afterCompletion 结束，超过阈值就落一条 trace。开关是 SLOW_SQL_RECORD_SWITCH，注意这里是严格等于小写字符串 "true" 才生效——TRUE、带空格的都不会开。这个坑我踩过。

第二层是业务事件埋点。引擎里到处是 EventCreator.business().createContextAsync("分页明细SQL生成", "UID:...") 这种写法，每个关键步骤都有个带 UID 的事件，start / end 一次就是一段计时。iuap-data-engine 仓库里这类 UID 去重后统计有 678 个——慢的时候能直接看出卡在哪一段。

第三层是处理器级耗时明细。StandardFlowExecutor#realExec 里维护一个 costDetail StringBuilder，每个处理器跑完追加一行「处理器名 + 耗时 X 毫秒」。虽然是异步提交，但每个 Future 单独计时，所以能看出是主查询慢还是 count 慢、是前置处理慢还是后置处理慢。

第四层是超时时的 SQL 现场。这块我觉得设计得挺好：realExec 拿到超时异常后，先调 publishTimeoutSqlExecuteEvent 去 ActiveSqlExecuteRegistry 里查「这条线程此刻正在执行哪条 SQL」，补发一条超时 SQL 快照，然后才 cancel。为什么这个顺序？代码注释写得很清楚——SQL 执行线程可能正卡在 JDBC 调用里，根本没机会走 finally 去写日志，所以监控侧会完全看不到这条超时 SQL。旁路补发就是为了补上这个盲区。

落库是两张表：ida_slow_sql_trace_info 记 SQL，ida_slow_report_trace_info 记报表诊断树。都带 trace_id，但没有外键，是逻辑关联。清理是每天 02:00 的一个定时任务，先抢 Redis 锁，然后按时间段分批删。」

代码依据

IntellivSlowInterceptor（iuap-common-core/analyze-report/.../interceptor/）实现 AsyncHandlerInterceptor； 引擎内 UID:P_DATA-COMMON-BE_* 事件去重后 678 个（按字符串去重，不代表 678 个独立业务场景）； StandardFlowExecutor#realExec 的 costDetail 与 TimeoutException 分支； publishTimeoutSqlExecuteEvent → ActiveSqlExecuteRegistry.peekCurrent(threadId)；清理任务 ScheduleClearSlowReportTrace。

Q10 一个报表查询很慢，你从哪一层开始查？

他在问什么

方法论。答「看日志」太浅，他要看你的排查路径是不是有层次。

怎么答

「我从外往里查，五层。

第一层：确认是不是查询慢。用户说报表慢，可能是页面渲染慢、可能是模型加载慢，跟查询没关系。先看 trace 里的总耗时，再看引擎入口的耗时——如果引擎只占 100ms，那问题不在引擎。

第二层：看是主查询慢还是派生查询慢。这是引擎特有的坑——主查询 200ms、COUNT(1) 3 秒，用户体感就是 3 秒。处理器耗时明细里能直接看出来。

第三层：看 SQL 长什么样。querySearchSql 能把当前查询的 SQL 打出来。重点看三件事：表是不是太多了（该裁的没裁）、条件有没有下推、IN 里是不是塞了几千个值。

第四层：看优化配置有没有生效。SqlOptimizeConfigUtil 匹配的是 tenant@user@object 三级 key，很容易配了但没匹配上——比如配在 tenant@ALL@object，但用户实际带了 userId，那就命中不到最细的那条。还有 rboRules 里如果写了不认识的规则名，是静默跳过的，不报错。

第五层：看数据库侧。到这一层才轮到 EXPLAIN、索引、统计信息。但我要强调一点：引擎能做的优化是有限的。如果 SQL 本身没问题、数据量就是大、索引就是缺，那不是引擎层的活。

还有一个特别常见的场景：报表刚加了一个维度，突然从 1 秒变 20 秒。这通常是新维度带进来一个 LEFT JOIN，而且关联键没索引。这种从「引擎层」看不出来，得看 SQL 变化——所以我一般会拿改动前后的 SQL diff 一下。」

代码依据

处理器耗时：StandardFlowExecutor#realExec 的 costDetail； SQL 文本：StandardFlowExecutor#querySearchSql 返回 QuerySqlProvider； 配置匹配：MatchSqlOptimizeConfig#matchSettingItems，key 为 po.getYtenantId() + "@" + po.getUserId() + "@" + po.getObjectId()； 超时控制：EngineExecuteHelper#getMaxTimeOut / checkEngineMaxExeTime，导出场景用另一套阈值。
